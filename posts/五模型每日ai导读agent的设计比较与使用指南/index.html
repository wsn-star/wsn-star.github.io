一、背景与目标

「青云志」技术博客需要每日产出一篇 AI 导读。纯手工写成本高、易断更；直接用大模型生成又面临三个核心问题：

  1. 事实不可信——模型会编造新闻
  2. 链接不可信——模型会编造 URL
  3. 长度失控——小模型写不满、漏条、格式跑偏

为此我们搭建了一条素材注入 + 本地模型生成 + 确定性兜底 + 质量校验的流水线，并逐步扩展到 5 个本地模型同时服务，用不同作者名区分产出，方便直接对比各模型能力。

本机硬件约束：RTX 5060 8GB 显存、15.7GB 内存——9B 模型无法全量 offload 到 llama.cpp，但 Ollama 能做到接近全量 GPU。这一差异直接决定了双后端的设计。

二、架构总览

素材层        scripts/news_input.json（当天新闻 + 最佳博文/视频，web_search 注入）
               ↓ 结构校验（畸形即退出）
生成层        本地模型 × 5（两个后端：llama-cli / Ollama）
               ↓ 模型输出
兜底层        确定性修复（补漏新闻 / 保真推荐小节 / 归一收尾与标题）
               ↓
校验层        硬校验 × 5（不过带修正提示重试，最多 3 次）
               ↓
产出层        content/posts/<日期>-每日AI导读[-N].md → build → deploy → GitHub Pages

五个入口脚本共用同一份核心逻辑（scripts/daily_ai_agent.py），各自只是注入不同参数：

入口 模型 后端 作者名 文件名后缀
daily_ai_agent.py qwen2.5-coder-7b llama-cli 无名散修 无
daily_ai_agent2.py Qwen3.5-9B-Revised llama-cli 青云·九章 -2
daily_ai_agent3.py Qwen3.5-9B-Claude-Opus-Distilled llama-cli 三剑客 -3
daily_ai_agent4.py qwen2.5:7b（Ollama） Ollama Ollama -4
daily_ai_agent5.py qwen-distill-q4:latest（Ollama） Ollama Oqwen -5

三、核心设计原理

3.1 素材注入，模型只写作

脚本不联网、不负责提供事实。当天新闻、最佳博文、最佳视频由调用方用 web_search 抓取后写入 news_input.json，模型只负责把素材润色成文章。这是"事实可信"的根本保证——模型没有机会编造。

3.2 链接绝不信任模型

推荐小节（今日AI博文推荐 / 今日AI视频推荐）的标题与 URL 一律以注入素材为准，由脚本 best_section() 精确保真构造。模型输出里的任何链接都不采信，因为小模型编造 URL 的风险不可接受。

3.3 确定性兜底（质量下限不靠模型自觉）

小模型能力有限，脚本用四个确定性函数保证产出结构：

  • complete_missing_news()：模型漏写的新闻以「其他要闻」小节补进正文——10 条新闻一条不漏
  • enforce_best_sections()：推荐小节保真覆写，素材为空则跳过
  • normalize_summary_title()：收尾小节标题归一（裸文本 今日小结、今日小结：正文 同行等变体统一为 ## 今日小结）
  • normalize_title()：front matter 标题冒号格式归一（全角 ：/空格 → 半角无空格）

3.4 质量校验闭环

硬校验（不过 → 带修正提示重试，最多 3 次）：front matter 完整、date 当天、小节标题不重复、新闻逐条覆盖（独有专名判定）、推荐链接齐全。

软校验（记日志不阻断）：字数过短、缺收尾小节。

关键词判定算法：优先英数专名（模型名/版本号），专名不足补中文片段，过滤概念词与高频中文词，无法判定的显式告警。

3.5 单后端约束

--backend 二选一（llama / ollama），一次运行只允许一种后端。llama-cli 与 Ollama 的模型、资源管理方式不同，并行只会互相干扰。

3.6 双后端的本质差异：续写 vs 对话

这是踩坑换来的关键认知：

后端 调用方式 模型行为 需要的技巧
llama-cli -p <prompt> 纯续写 把 prompt 当"接着写"的上下文 → 直接产出 Markdown 无需额外处理
Ollama /api/chat 对话消息 倾向"回应对话" → 把指令当"待分析输入" system 消息声明"直接输出文章"

实测：llama3 基座模型无论走 chat 还是 generate，都会把写作指令当输入分析（"It seems like you're using Markdown…"），无法胜任格式任务；qwen2.5:7b 指令版 + system 消息则稳定遵循。选型时"指令/续写调优模型"远比"聊天基座模型"适合格式生成。

3.7 GPU 策略：llama-cli 与 Ollama 的显眼差距

本机 8GB 显存下实测：

指标 llama-cli（9B, -ngl 12） Ollama（9B 自动管理）
显存占用 7224 MiB 7020 MiB
GPU 利用率峰值 ~19% 94%
生成速度 ~68s（完整导读） ~20s / 43 tok/s

结论：llama-cli 的 -ngl 12 是它自己的层数上限（-ngl 14 临界、-ngl 16 OOM），Ollama 内部做了更聪明的显存管理，能把 9B 模型几乎全量塞进 GPU。新模型优先走 Ollama 后端，无需手动 -ngl 调优。

3.8 风格契约

站点外观保持仙侠风（品牌文案、配色），博文标题与正文一律正式技术风——导读标题如 每日 AI 导读:2026-09-18，禁止文学化/武侠化表达。

四、五模型逐一详解

4.1 qwen2.5-coder-7b（无名散修）——流水线元老

  • llama-cli 纯 CPU（-ngl 0），约 50-90s/篇
  • 首个验证可用的模型，奠定了"续写式 prompt 能稳定出 front matter"的基线
  • 特点：逐条罗列新闻，主题小节相对朴素

4.2 Qwen3.5-9B-Revised（青云·九章）——首个 9B

  • llama-cli，-rea off -ngl 12，约 68-100s/篇
  • 关键发现：Qwen3.5-9B 系列默认输出 [Start thinking] 思考块挤占正文 → 必须 -rea off
  • 特点：主题归类别更清晰，能归纳"综合小节"，产出接近综述而非要闻列表

4.3 Qwen3.5-9B-Claude-Opus-Distilled（三剑客）——推理蒸馏版

  • llama-cli，-rea off -ngl 12，约 2min/篇
  • 名字含义：结合 Qwen + Claude + Opus 蒸馏优点
  • 特点：内容密度高，能把多条模型新闻整合进「能力演进」小节并注明 SOTA，表达最紧凑

4.4 qwen2.5:7b via Ollama（Ollama）——首个 Ollama 后端

  • Ollama /api/chat + system 消息，约 17-25s/篇，GPU 利用率 ~94%
  • 验证了"Ollama 全 GPU + system 消息"这套组合的可行性
  • 特点：速度快一个量级，格式遵循稳定

4.5 qwen-distill-q4:latest via Ollama（Oqwen）——9B 蒸馏最快

  • Ollama，约 20s/篇，一次通过硬校验
  • 9B 蒸馏版在 Ollama 全 GPU 下兼顾质量与速度

六、使用指南

6.1 前置条件

  • Python 3.12（conda env ai-agent）
  • llama-cli：C:\llama\llama-cli.exe + GGUF 模型
  • Ollama：服务运行中（ollama serve），已 pull 对应模型

6.2 生成命令

# 素材准备：web_search 抓当天新闻/博文/视频 → 写入 scripts/news_input.json

# 各模型生成（可选 --draft 只预览不写文件）
PYTHONIOENCODING=utf-8 $PY scripts/daily_ai_agent.py [--draft]
PYTHONIOENCODING=utf-8 $PY scripts/daily_ai_agent2.py [--draft]
PYTHONIOENCODING=utf-8 $PY scripts/daily_ai_agent3.py [--draft]
PYTHONIOENCODING=utf-8 $PY scripts/daily_ai_agent4.py [--draft]
PYTHONIOENCODING=utf-8 $PY scripts/daily_ai_agent5.py [--draft]

6.3 发布

bash deploy.sh "内容: 每日AI导读 <日期>"

6.4 故障排查速查

现象 原因 处理
缺 front matter（3 稿失败） 推理模型输出思考块 llama-cli 加 -rea off；Ollama 用 system 消息
模型把指令当输入回应 聊天基座模型 换指令版（qwen2.5:7b），加 system 消息
--llama-args=-rea,off 报错 argparse 把 -rea 当选项 用等号形式传值
9B OOM 8GB 显存限制 llama-cli -ngl 12；或改用 Ollama 后端
Ollama 连接拒绝 服务未运行 ollama serve 并保持窗口

七、选型建议

  • 追求速度：Ollama 后端（agent4/5），20 秒出稿
  • 追求质量：Claude-Opus 蒸馏（agent3）内容最紧凑；Qwen3.5-9B-Revised（agent2）综述感强
  • 稳定性优先：qwen2.5:7b（agent4）格式遵循最稳
  • 新模型优先走 Ollama：自动全 GPU，免去 -ngl 调优
  • 避免：聊天基座模型（如 llama3）做格式生成任务

八、结语

这套流水线的核心经验可以一句话概括：把"事实"与"格式"交给确定性代码，把"表达"交给模型。素材注入保证事实可信，确定性兜底保证结构统一，质量校验保证不产出坏稿——模型只负责它擅长的润色。五模型并存后，每天可以一次生成五篇导读，直接对比各家能力差异，也方便逐步淘汰表现差的模型。
