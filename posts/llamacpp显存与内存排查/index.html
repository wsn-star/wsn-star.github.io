llama.cpp 显存够用却大量占用内存（RAM）的排查与修复

一、问题现象

在 8GB 显存的机器上跑本地大模型，一个常见困惑是：显存明明显示够用，内存（RAM）却依然被大量占用。模型文件只有几个 GB，跑起来却"不止那几个 GB"，系统内存被吃满，Windows 开始疯狂换页，整机变卡。

二、根因：模型文件 ≠ 运行时占用

一个 4.8GB 的 GGUF 模型，运行时占用的资源远不止 4.8GB：

  1. 模型权重本身（约 4.8GB，全部或部分驻留显存）
  2. KV Cache（上下文缓存）——llama.cpp 启动时按 -c（上下文窗口大小）预先分配，用来记忆对话/续写上下文
  3. 运行时开销——分词器、采样器、系统库等

关键在第二项：KV Cache 的大小与上下文窗口成正比。-c 4096 与 -c 32768 的缓存差一个量级——上下文设得越大（比如 32k / 64k），缓存越容易额外吃掉 2GB–4GB 显存。

8GB 显存上的"饱和算式"

以本机 RTX 5060 8GB 为例：

4.8GB（模型权重） + 3GB（KV Cache） = 7.8GB ≈ 8GB 显存打满

一旦打满，Windows 就会把溢出的部分换到系统内存——表现就是"显存恰好打满、内存却大量占用"，两者同时告急。

三、三个常见成因

llama.cpp 显存够用却依然大量占用 RAM，通常来自以下三条，按排查顺序列出：

  1. 未开启 GPU 硬件加速编译：llama.cpp 二进制没带 CUDA 支持时，-ngl 形同虚设，所有层都在 CPU 上跑，权重全量留在内存
  2. 未正确设置把全部层加载到显存：-ngl 层数设得过小（如 -ngl 0 纯 CPU），部分层驻留内存
  3. 操作系统 mmap 机制：默认 mmap 把模型文件映射到内存，文件页缓存会吃 RAM（--no-mmap 可关闭）

四、修复：先把上下文窗口钳到安全基线

第一步（最关键），把上下文窗口钳到安全值：

llama-cli -m <model>.gguf -c 4096   # 或 -c 8192

-c 2048 同样安全（本仓库流水线默认即 2048，远低于 32k 阈值，KV Cache 规模可控）。

第二步，逐个变量排查。在命令末尾追加：

llama-cli -m <model>.gguf --no-mmap -c 4096 -ngl -1
  • --no-mmap：关闭 mmap，排除"文件被映射进内存"这一变量
  • -c 4096：钳住 KV Cache 规模
  • -ngl -1：把全部层 offload 到 GPU（前提：二进制带 CUDA 支持，且显存放得下）

第三步，若内存占用仍然很高，把 llama.cpp 启动时前 20 行终端输出贴出来排查——带 ggml_cuda 的行会直接说明问题出在哪：是否识别到 GPU、实际 offload 了多少层、KV Cache 分配了多大。

五、与本仓库流水线的对照

本仓库每日导读流水线（scripts/daily_ai_agent.py）已踩过这条线，参数现状：

后端 上下文 GPU 参数 说明
llama-cli（7B） -c 2048 -ngl 0 纯 CPU 7B 小模型 CPU 即可满足
llama-cli（9B） -c 2048 -ngl 12 8GB 显存下 9B 的层数上限（-ngl 14 临界、-ngl 16 OOM）
Ollama（9B） Ollama 自动 自动管理 GPU 利用率 ~94%，接近全量进显存

对照上面的排查清单：

  • 上下文已达标：全部入口统一 -c 2048，KV Cache 规模远低于 32k 阈值，无需再加 -c 4096 钳制
  • 9B 无法 -ngl -1：8GB 显存放不下 9B 全量层，实测上限 -ngl 12；这正是当初引入 Ollama 后端的直接原因
  • Ollama 是终局方案：内部自动管理 KV Cache 与层 offload，GPU 利用率 94%（llama-cli 仅 ~19%），从源头避开 mmap 与 -ngl 手动调优问题

六、小结

排查顺序一句话：先钳上下文（-c 4096 / -c 8192），再关 mmap（--no-mmap），最后看 ggml_cuda 头几行确认 GPU offload 是否生效。模型文件大小只是起点——KV Cache 规模与层 offload 策略，才是 8GB 显存机器上内存/显存账本的真正变量。
